## 1. Current State Summary

The application is in an intermediate state where core data models and integrations (Supabase, Meta) are implemented, but the routing and role authorization layers are incomplete. 

**Critical Issues:**
- `app/login/page.tsx` unconditionally routes all users to `/dashboard`.
- Middleware unconditionally routes authenticated users from `/login` and `/` to `/dashboard`.
- Admins land on the client-facing dashboard and must manually navigate to admin routes (e.g., `/dashboard/admin/clients`).
- The client invitation flow does not reliably route to the password setup page (`/invite/accept`), resulting in clients with active sessions but no passwords.
- The `/invite/accept` page lacks an authentication guard.
- The production database contains active demo users, and the real admin account is named "Demo User".
- The dashboard displays hardcoded demo data alongside real data.
- The Meta insights sync (Step 09) is broken due to a status inconsistency (`'connected'` vs `'active'`) and a schema mismatch in `sync_logs`.
- Meta API versions are split (`v26.0` for OAuth, `v21.0` for data).

## 2. Root Causes

- **Routing:** Post-login routing and middleware do not evaluate the user's role before redirecting.
- **Invitation Flow:** The exact behavior of Supabase's PKCE invitation flow (`inviteUserByEmail`) regarding the `?next=/invite/accept` parameter during the redirect chain is unverified. When reached, the target page doesn't enforce a session requirement, leading to silent failures.
- **Admin Portal:** Admin routes were built as children of the client dashboard (`/dashboard/admin/*`) rather than in a dedicated namespace (`/admin/*`), leading to shared layouts and confused routing.
- **Inconsistencies:** Manual, disjointed updates caused schema mismatches (e.g., `sync_logs` columns expected by cron not present in DB) and hardcoded values left over from early prototyping.

## 3. Target Authentication Architecture

The core tenet is strict role resolution from trusted server-side data, completely isolated from client-side state or email-based heuristics.

**Target Flow:**
1. `/login`
2. `signInWithPassword()` succeeds
3. Redirect to `/auth/redirect` (a new Server Component)
4. Server-side `getCurrentProfile()` retrieves the user's role
5. Role Resolution:
   - `role IN ('super_admin', 'admin')` → Redirect to `/admin/dashboard`
   - `role = 'client'` → Redirect to `/dashboard`

## 4. Target Admin Portal Architecture

- **Dedicated Namespace:** Move all admin routes to an `/admin/*` namespace.
  - `/admin/dashboard` (Overview)
  - `/admin/clients` (Client Management)

- **Layout & Navigation:** Create `app/admin/layout.tsx` as the central server-side authorization boundary for the entire admin route tree. This layout must call `requireAdmin()` before rendering any admin children.
- **Deep Authorization:** While the layout provides a coarse UI boundary, sensitive server actions and API routes must **still independently enforce** `requireAdmin()`. Authorization cannot rely on UI hiding or middleware alone.
- **Component Reuse:** Reuse existing data components (e.g., `ClientManager.tsx`, `AdAccountsManager.tsx`) within the new namespace.

- **Authorization:** Enforce `requireAuth()` server-side on the dashboard layout.
- **Isolation:** Maintain existing RLS policies that restrict client data access strictly to their assigned organization and campaigns.

## 7. Role Resolution Strategy

Role resolution and authorization must remain completely distinct concepts:

- **AUTHENTICATION:** Is the user logged in? (Determined by Supabase session token)
- **ROLE RESOLUTION:** Is the user an admin or a client? (Determined by fetching `public.profiles.role` using `auth.uid()`)
- **ROUTE AUTHORIZATION:** Can the user access `/admin` or `/dashboard`? (Enforced by `app/admin/layout.tsx` calling `requireAdmin()`, and pages calling `requireAuth()`)
- **DATABASE AUTHORIZATION:** What rows can the user see/change? (Enforced by PostgreSQL RLS using `get_auth_role()`)

These four layers must remain consistent and strictly enforced.

## 8. Middleware Strategy

Middleware should remain a **coarse** authentication and session layer. It should NOT be the primary role authorization system.

**Responsibilities:**
- Refresh the Supabase session token.
- Prevent unauthenticated access to `/dashboard*` and `/admin*` (redirect to `/login`).
- Handle root `/` entry (redirecting authenticated users to the `/auth/redirect` router).

**What it should NOT do:**
- It should not query the database to determine roles.
- It should not enforce the boundary between `/dashboard` and `/admin`. Precise authorization remains the job of `app/admin/layout.tsx`, server actions, API routes, and RLS.
